### 0.4 项目定位与范围决策（Scope Decisions）

**定位（决定了后面所有取舍）**：这是一个用于 **Agent 开发方向实习的工程项目 / 学习项目**，不是商业级 Agent 平台。

由此推出的第一原则：**优先保证核心链路的完整性与代码质量，而不是能力数量**。核心链路 =

```text
Agent Runtime → Tool Calling → Workflow → RAG → Trace / 评测（脚本）
（Memory 在 MVP 只做"短期窗口"，长期记忆为迭代 A；MCP 为迭代 B）
```

第一阶段（2–3 周）**只做上面这条链路**（SD-13，停止线见 0.5.1）：MCP（SD-16）与长期记忆（SD-15）**整体延后到迭代**，但表结构、接口位置与接管模块（`MCPToolAdapter` / `LongTermMemory`）都已写死在文档里，迭代时按原文实现即可。

#### 0.4.1 范围决策表（SD，实施时不得擅自扩大）

- **SD-1** —— **Workflow 不支持并行分支**：一个节点只允许「单条 `next`」或「`branch` 多路择一」，出现多条无条件出边 → `WORKFLOW_INVALID_GRAPH`（422）
  - 理由：串行图已能表达大纲 Phase 3 的全部示例（`Start→Agent→Tool→Agent→Condition→End`）；并行会引入 join 语义与状态合并难题
  - 预留点：`node_runs` 已有 `iteration`/`attempt`；`WorkflowState` 用 dict，未来做并行不需改表
- **SD-2** —— **同一 step 内的多个 `tool_calls` 顺序执行**
  - 理由：工具多为同步 IO/本地计算，并行收益低而错误归因变难；顺序执行让 Trace 与 `tool_invocations.call_index` 的语义最简单
  - 预留点：`call_index` 字段已预留；执行点集中在 `ToolExecutor`，未来换 `asyncio.gather` 只改一处
- **SD-3** —— **不做多用户、不做鉴权**：单用户本地模式，`conversations.owner_key` 固定 `local`
  - 理由：实习项目以功能链路为重点；鉴权会牵连会话隔离、密钥分级、前端登录态等整条支线
  - 预留点：`owner_key` 字段与鉴权中间件位置（`api/deps.py`）已预留；错误码 `AUTH_*` 已定义但**不启用**
- **SD-4** —— **`python_execute` 采用子进程 + 白名单，不追求生产级隔离**：`asyncio.create_subprocess_exec(sys.executable, "-I", "-c", code)` + AST `import` 白名单校验 + cwd 限定沙箱 + 超时杀进程组 + 输出截断
  - 理由：目标是演示"平台能安全地承载代码执行"这条工程链路（权限分级 → 显式开关 → 沙箱 → 审计），容器/gVisor/WASM 属基础设施工程，超出项目重点
  - 预留点：沙箱入口只有 `tools/sandbox.py` 一个文件，未来替换为容器执行器不影响调用方
- **SD-5** —— **不支持多模态**：消息 `content` 仅文本
  - 理由：多模态会改动消息模型、Provider 抽象与前端渲染三处，投入产出比低
  - 预留点：`messages.content` 保持 TEXT；若扩展可加 `content_parts` JSON 列（非破坏性迁移）
- **SD-6** —— **不做 Workflow 可视化编辑器（拖拽）**：前端只做 **JSON/YAML 编辑 + 校验提示 + 只读图渲染**
  - 理由：大纲 Phase 3 已明确取舍；拖拽编辑器是独立的前端工程
  - 预留点：`definition` JSON 已是唯一事实来源，编辑器只是另一种输入方式
- **SD-7** —— **不引入 A2A / 多 Agent 协作协议**
  - 理由：Agent 间协作在本项目中用 **Workflow 的 `agent` 节点**即可表达；A2A 是跨厂商互操作标准，与学习目标无关
  - 预留点：`workflow` 节点已可引用任意 Agent，等价能力已具备
- **SD-8** —— **SQLite 为唯一目标数据库**，不引入 PostgreSQL
  - 理由：单用户本地场景下 SQLite 完全够用，省掉一套运行时依赖与迁移验证成本
  - 预留点：`DATABASE_URL` 保持可配置；`db/base.py` 的 JSON 方言分支保留但不在 CI 中验证
- **SD-9** —— **保留 `asyncio` 任务模型与基础限流**：`max_concurrent_runs` 全局闸门 + 工具级令牌桶 + `asyncio.wait_for` 超时 + 指数退避重试
  - 理由：这是"工程化能力"的体现点，成本低、收益高，且是 SSE 流式与长任务的基础
  - 预留点：限流器与 `TaskRunner` 各自一个模块，未来可换成外部组件
- **SD-10** —— **Workflow 引擎先只实现 `SimpleEngine`**（纯 `asyncio`，零第三方依赖）；`LangGraphEngine` 降级为**可选加分项**，且**必须先有 conformance 测试才能加第二个实现**
  - 理由：两个引擎同时维护是典型的过早工程化；先把图语义、断点续跑、事件转发做对，比"可替换"的演示更重要
  - 预留点：`WorkflowEngine` Protocol + `test_engine_contract.py` 模板保留，加第二个实现时只需参数化扩展
- **SD-11** —— **向量库只用 Chroma**（生产路径）+ `InMemoryVectorStore`（测试）；**不实现 `QdrantVectorStore`**
  - 理由：一套实现即可覆盖 RAG 全部需求，第二套后端只是重复劳动
  - 预留点：`VectorStore`/`MemoryBackend` Protocol 保留；`Settings` 中**不再预置** `qdrant_url`（未实现的能力不配配置项）
- **SD-12** —— **不自动清理** `spans` / `messages` / 旧 Run
  - 理由：演示规模（≤ 数万行）下 SQLite 无压力，清理逻辑属于运维工程
  - 预留点：6.5 的 `maintenance/*` 接口已预留手动触发
- **SD-13** —— **实施顺序以 MVP 闭环为唯一口径**：第一阶段（2–3 周）只交付 **0.5 的 MVP 五件套**（Agent Runtime → Tool Calling → Workflow → RAG → Trace/评测），其余能力一律进 Backlog；时间不足按 0.5.4 的顺序砍
  - 理由：求职/实习场景下"**能当场演示的一条完整链路**"远胜"很多半成品能力"；先把闭环做透，才有可讲的设计与取舍
  - 预留点：0.5.1 给出的"最小实现口径"把每个模块的停止线写死，避免无限打磨
- **SD-14** —— **反过早工程化三条红线**：① 不写第二套实现（先跑通，再抽象）；② 不为未实现的能力添加配置项/枚举值/空实现类；③ 抽象层只在出现**第二个真实调用方**时才抽
  - 理由：明确的项目定位是学习项目，代码要"能讲清楚为什么这么写"
  - 预留点：每个里程碑的 DoD 都只验收"可运行 + 可测试"，不验收"可扩展"
- **SD-15** —— **复杂 Memory 系统延后**：MVP 只做**短期记忆**（= `messages` 的窗口装配，`strategy=window`），不建 `memory_items` 表、不做向量记忆召回、不做 LLM 自动抽取、不提供 `/memories` 接口
  - 理由：长期记忆是"锦上添花"，却要引入第二个向量集合 + 抽取 Prompt + 去重/过期策略，2–3 周内性价比最低
  - 预留点：`agents.memory_config` 保留（其中 `long_term` 子字段先不生效）；4.3.2/4.3.3 的设计文档完整保留，迭代时按原文实现
- **SD-16** —— **MCP 整体延后**（含 stdio 最小实现）：MVP 的 Tool Registry 只有 `builtin` 与 `api` 两类来源
  - 理由：MCP 的传输/握手/连接池是一条独立支线，对"闭环演示"无增益；且会引入可选依赖与降级分支，增加不确定度
  - 预留点：`ToolType.mcp`、`SpanType.mcp`、`ToolExecutor` 的 mcp 分派点、2.10 表结构与 4.7 设计全部保留；接管点只有 `MCPToolAdapter` 一处
- **SD-17** —— **权限收敛为"分级 + 开关"，不做审批后台**：`safe/guarded/dangerous` 继续用于校验 `allowed_paths`/`allowed_hosts`/调用次数；`dangerous`（`python_execute`）默认禁用，需在 `Settings` 显式开启；`require_approval=true` 的工具在无审批通道时**直接拒绝**（`TOOL_PERMISSION_DENIED`），Run 不挂起
  - 理由：交互式审批需要 `approvals` 表 + 挂起/续跑状态机 + 前端弹窗 + 超时语义，是 MVP 里最容易被低估的一块复杂度；"危险默认关闭 + 显式开启"已足够演示安全设计
  - 预留点：`approvals` 表结构与 4.5.4 的挂起语义保留在文档中；`PermissionDecision.approval` 与 3 个 SSE 事件在附录中标注 Backlog
- **SD-18** —— **Evaluation 收敛为"Trace + 基础指标 + 脚本评测"**：`runs/spans/traces` 落库 + `GET /stats/overview` + `scripts/evaluate.py` 读 `configs/eval/*.yaml` 用例集输出报告（md/json）；**不建** `eval_suites/eval_cases/eval_runs/eval_results` 四张表，不做评测页面与历史对比
  - 理由：大纲要的是"有可复现的评测结果"，脚本化即可满足；把用例入库 + 页面化是评测平台的工程量，与 MVP 无关
  - 预留点：4.9.2 的指标定义与 4.9.3 的断言实现是**同一份口径**，将来 DB 化时 Runner 与断言代码零改动（只换用例来源）
- **SD-19** —— **里程碑口径以本文档 0.5 的 M1–M3 为准**；第 7 章的 Phase 0–8 编号**保留仅用于追溯《设计大纲》**，其中 Phase 4（Memory 完整形态）、Phase 6（MCP）、Phase 7（评测台）、Phase 8（增强项）为 **Backlog，不排期、不计入 MVP 的 DoD**
  - 理由：两个"排期视图"必须有一个权威，否则会被"大纲里写了要做"倒逼扩范围
  - 预留点：7.0.2 给出 Phase ↔ MVP/Backlog 的对照表；Backlog 项完成后在附录 D 的路线图勾选

### 0.5 第一阶段 MVP 范围与里程碑（2–3 周）

> **结论先行**：项目分两层交付 —— **MVP（第一阶段，2–3 周）** 与 **Backlog（迭代项）**。
> MVP 的验收标准是"**一条完整闭环可以当场演示，且每个模块都有测试和清晰接口**"，而不是"生产级能力齐备"。
> 相比功能数量，优先保证：**模块划分、接口设计、可扩展性、代码质量**。

#### 0.5.1 MVP 五件套与"做到哪算完成"

- **Agent Runtime（M1）**：Provider 注册 + 连通性测试；Agent 配置 CRUD（Prompt / 模型 / 工具 / KB / 循环上限 / 超时）；Conversation + `messages` 落库；**SSE 流式**输出；`runs`/`spans` 基础 Trace；`GET /stats/overview` 基础指标
  - 不做 → Backlog：密钥分级、Prompt A/B、模型路由与降级、断线续答
- **Tool Calling（M2）**：Tool Registry（5 个内置工具）+ LLM function schema 生成；`ToolExecutor` **顺序**执行（SD-2）；`safe/guarded/dangerous` 分级校验（路径 / host / 次数）；危险工具默认禁用 + Settings 开关；错误**结构化回填**；`tool_invocations` 明细
  - 不做 → Backlog：交互式人工审批（SD-17）、工具并行（SD-2）、MCP 工具（SD-16）、`api` 工具的复杂鉴权
- **Workflow（M2）**：`Start → Agent → Tool → Condition → End` **串行图**（`SimpleEngine`，SD-10）；定义 JSON 静态校验（含"禁止多出边" SD-1）；`node_runs` + `state` 落库；失败可 `resume`；前端 JSON 编辑 + 只读图
  - 不做 → Backlog：并行分支 / join、`human` 节点（SD-17）、拖拽编辑器（SD-6）、子图复用、定时触发
- **RAG（M3）**：KB CRUD；**md/txt** 上传 → 摄取（loader → splitter → embedding → Chroma）；向量检索；两种检索模式（`kb_search` 工具 / Agent 绑定 KB 的固定预检索）；引用来源回显；命中为空时拒答
  - 不做 → Backlog：pdf / 网页 loader（pdf 视时间可选）、rerank、混合检索、文档版本管理、多 Collection 路由
- **Trace / Evaluation（M3）**：`runs/spans/traces` 落库与查询 API + Trace 树；`scripts/evaluate.py` 读 `configs/eval/*.yaml` 跑用例集 → 输出报告（md/json）；指标口径与 4.9.2 一致
  - 不做 → Backlog：评测台（四张表 + 页面 + 历史对比，SD-18）、自动清理归档（SD-12）、告警

**贯穿 MVP 的工程性要求**（不因赶工而放弃）：分层与依赖方向（1.2）、统一错误模型（1.6）、结构化日志与 Trace 上下文（1.5.1/1.5.2）、超时/重试/限流（1.5.3/1.5.4）、单测 + 契约测试（第 9 章）、**三个 Demo Agent 纯配置差异**（第 8 章）。

### 1.2 分层与依赖方向（不可逆）

```text
api  →  services  →  db/models
                 ↘  runtime/*  →  runtime/observability
frontend  →  /api/v1 (HTTP + SSE)  →  api
```

- **api**：只做协议转换、参数校验、组装 DTO；不写业务分支、不直接调 `runtime`（`chat.py` 例外：它订阅 Run 事件流）。
- **services**：事务边界、实体 CRUD、跨实体编排。
- **runtime**：纯执行逻辑，**禁止 import `services` / `api`**；需要的实体数据通过入参 dataclass 传入，保证可单测、可脱离 DB 运行。
- **runtime 内部依赖**：`agent` 可依赖 `llm` / `tools` / `memory` / `rag` / `observability`；`workflow` 可依赖 `agent`；反向依赖一律禁止。
- 每个可替换家族（LLM / Embedding / VectorStore / Memory / WorkflowEngine / Tool）都有 `base.py` 抽象 + `registry.py` 按 `kind` 实例化，业务代码只持有抽象类型 —— 落实大纲原则 3。

### 1.5 横切能力（所有模块统一复用）

#### 1.5.1 日志

`structlog` JSON 输出，每条日志自动注入 `request_id` / `trace_id` / `span_id`（来自 `observability/context.py` 的 `ContextVar`）。`dev` 环境用彩色 console renderer，`prod` 用 JSON。日志行格式：

```json
{"ts":"2026-09-29T12:00:00.123Z","level":"info","event":"llm.request",
 "trace_id":"…","span_id":"…","model":"qwen-plus","messages":3,"stream":true}
```

#### 1.5.2 Trace 上下文传播

- `Tracer.start_run(...)` 在 Run 起点创建根 span，把 `trace_id` 写入 `ContextVar`；`asyncio` 任务通过 `contextvars.copy_context()` 继承。
- `Tracer.span(span_type, name)` 作为 `async with` 上下文管理器使用，退出时自动落库（含 `status`、`latency_ms`、`error_*`）。
- SSE 推送与数据库写入**共用同一个 span 对象**，保证前端展示与 `spans` 表一致。

#### 1.5.3 超时 / 重试 / 熔断

| 场景 | 超时 | 重试 | 说明 |
|---|---|---|---|
| LLM 调用 | `LLM_TIMEOUT_SECONDS`（60s） | `LLM_MAX_RETRIES`（2） | 429 / 5xx / 连接错误，退避 `0.5/1/2s` |
| Tool 执行 | `TOOL_DEFAULT_TIMEOUT_SECONDS` | 默认 0 | `api` 可配 `retry_times` |
| Run 整体 | `AGENT_RUN_TIMEOUT_SECONDS` | — | → `run.failed` + `RUN_TIMEOUT` |
| MCP 连接 | 10s / 60s | 1 次重连 | 标记 `status=error`（**Backlog**） |

> 补充：表中已省写默认值 —— Tool 15s、Run 180s、MCP 建连 10s / 调用 60s。LLM 重试只允许在**首个 token 到达前**进行（首 token 后重试会造成重复内容）；工具超时必须 kill 整个子进程组。

`core/retry.py` 提供 `@async_retry(times, base_delay, retry_on=...)`，**禁止在业务代码里裸写 try/sleep 循环**。

#### 1.5.4 限流与并发

- 进程内令牌桶 `core/ratelimit.py`：
  - `llm:{provider_id}`：默认 5 req/s（可配），429 时降速；
  - `tool:{tool_id}`：默认 10 req/s；
  - 单会话最多 1 个活跃 Run（并发请求返回 `CONFLICT`）。
- 全局并发闸门：`asyncio.Semaphore(settings.max_concurrent_runs)`（默认 4），防止本地模型/API 被打满。

#### 1.5.5 幂等与取消

- 写接口支持 `Idempotency-Key` 头（Redis 不引入，落 `runs`/`messages` 唯一约束 + 内存 LRU，TTL 10 分钟）。
- `POST /conversations/{id}/messages` 返回的流内首事件带 `run_id`；`POST /runs/{run_id}/cancel` 通过 `asyncio.CancelledError` 中断，Run 置 `canceled`，已产生的 `messages` 保留。

### 1.6 错误模型

**统一异常基类**（`core/errors.py`）：

```python
class AppError(Exception):
    code: str = "INTERNAL_ERROR"      # 见附录 A
    http_status: int = 500
    message: str = "Internal error"
    details: dict[str, Any] = {}      # 仅存放安全、可展示的信息
```

**错误响应体**（与成功响应体结构对称）：

```json
{
  "error": { "code": "TOOL_PERMISSION_DENIED",
             "message": "Tool 'file_write' is disabled (set FILE_WRITE_ENABLED=true to allow it)",
             "details": { "tool_name": "file_write", "permission_level": "guarded" } },
  "meta":  { "request_id": "…", "trace_id": "…" }
}
```

**映射规则**：

| 来源 | 转换 |
|---|---|
| `AppError` 子类 | 按其 `code` / `http_status` 返回 |
| Pydantic `ValidationError` | `VALIDATION_ERROR` / 422（含字段级 `details`） |
| SQLAlchemy `IntegrityError` | 唯一约束 → `CONFLICT` / 409；外键 → 422 |
| LLM SDK 异常 | `MODEL_*`（见下） |
| 未捕获异常 | `INTERNAL_ERROR` / 500，不回传堆栈 |

> LLM SDK 异常的具体映射：`MODEL_RATE_LIMITED`(429) / `MODEL_TIMEOUT`(504) / `MODEL_AUTH_FAILED`(502) / `MODEL_BAD_REQUEST`(502)；未捕获异常会把堆栈写日志、只回 `request_id` 供排查。

AppError 的完整错误码表见**附录 A**；每个错误码标注了**引入阶段**，便于按 Phase 实现。

设计取舍（写死，避免后续反复）：

1. **`agents.tool_ids` / `knowledge_base_ids` 用 JSON 数组而非关联表**：规模小、无需按工具反查 Agent，省一张表；代价是外键不强制 —— 由 `agent_service` 在写入时校验存在性（Phase 2 起有单测覆盖）。

3. **所有外部 IO 的输入输出都走 span 的 `input`/`output`（带截断）**，业务表不重复存大文本（`messages.content` 是例外，它是会话的事实来源）。

> **`require_approval` 在 MVP 中的语义（SD-17）**：没有审批通道时的等价物是"**未开启即拒绝**"。`require_approval=true` 的工具只有在 `Settings` 显式开启后才能执行（`file_write` → `FILE_WRITE_ENABLED=true`；`python_execute` → `PYTHON_EXECUTE_ENABLED=true`），否则该次调用直接返回 `TOOL_PERMISSION_DENIED`（错误回填给 LLM，Run 不挂起）。字段名保留是为了 Backlog 迭代 C 加回审批 UI 时不用改数据。

内置工具的五条初始定义（Phase 2 由 `alembic` 数据迁移写入，即大纲"第一阶段实现少量内置 Tool"）：

| name | level / require_approval | 关键限制 |
|---|---|---|
| `calculator` | safe / false | 仅 AST 白名单运算，**禁止 eval** |
| `web_search` | guarded / false | `allow_network=true` + host 白名单 |
| `file_read` | safe / false | 限 `SANDBOX_ROOT` 内，防 `../` 穿越 |
| `file_write` | guarded / **需显式开启** | 同上；单文件 ≤ 1 MB |
| `python_execute` | dangerous / **默认禁用** | 子进程 + AST 白名单 + 沙箱 cwd（SD-4） |

> 细节：`calculator` 的白名单运算为 `+ - * / ** // %` 与数学函数；`web_search` 无 API Key 时返回 `TOOL_DISABLED`；`file_read`/`file_write` 要求 `resolve()` 后仍在 `allowed_paths` 内，写入仅允许白名单文件、可追加或覆盖；`python_execute` 另含超时杀进程组与输出截断（见 4.2.4，**非安全边界**）。

> 这 5 个即大纲"第一阶段实现少量内置 Tool"的落地：`web_search` 对应大纲的 `web/search`，是 MVP"多个基础工具调用"的主力；`file_write` 需 `FILE_WRITE_ENABLED=true`、`python_execute` 需 `PYTHON_EXECUTE_ENABLED=true` 才可用（SD-17）。

> **MVP 的 Tool Calling 演示不依赖审批**（SD-17）：默认路径用 `calculator` + `file_read` + `web_search`（+ 可选 `kb_search`）即可展示"Agent 自主决定调工具 + 参数校验 + 错误回填"；`python_execute` 只作为"危险工具默认关闭、显式开启后可用"的开关式演示（Backlog 迭代 C 再补人工审批交互）。

**Run 状态机**（Chat 与 Workflow 节点复用同一套；`cancel()` / `fail()` 的合法来源写死如下）：

```text
pending ──start──> running ──┬── 成功（无更多 tool_call）──> succeeded
                             ├── 异常 / 超时 ──────────────> failed
                             └── 用户取消 ────────────────> canceled
```

> **SD-17 收窄**：MVP **没有**"挂起等审批"这一态 —— 需要 `require_approval` 的工具在未显式开启时**直接拒绝**（该次调用记 `TOOL_PERMISSION_DENIED` 并把错误回填给 LLM，Run 继续或按循环上限结束）。
> Backlog 迭代 C 加回审批后，状态机补上"挂起（`status` 仍为 `running`，用 `approvals` 表表达）→ 批准后继续 / 拒绝后按规则收尾"这一支。

约定：进入终态后**禁止再次变更**（`RUN_ALREADY_FINISHED` / 409）；`runs` 行在 Run 开始时即插入（`status=running`），确保崩溃后能查到"孤儿 Run"，由 `Phase 3` 的启动自检把超过 `timeout_seconds × 2` 的 running 标记为 failed(`RUN_ABANDONED`)。

`definition` 规范（对应大纲 Phase 3 的 JSON 示例，做了正式化）：

```json
{
  "nodes": [
    { "id": "start",  "type": "start",  "name": "开始",  "next": "planner" },
    { "id": "planner","type": "agent",  "name": "规划",  "agent_id": "agt_planner",

    { "id": "search", "type": "tool",   "name": "检索",  "tool_name": "web_search",
      "arguments_template": { "query": "{{state.plan}}" }, "output_key": "hits", "next": "router" },
    { "id": "router", "type": "condition","name": "是否命中",
      "branches": [ { "when": "len(state.hits) > 0", "next": "writer" } ], "default_next": "end" },
    { "id": "writer", "type": "agent",  "name": "撰写",  "agent_id": "agt_writer", "next": "end" },
    { "id": "end",    "type": "end",    "name": "结束" }
  ],
  "edges": [],
  "config": { "max_steps": 30, "timeout_seconds": 600, "recursion_limit": 50 }
}
```

- 节点类型与大纲一致：`start / agent / tool / condition / end`，另加 `retriever`（知识库检索节点，MVP 需要，属 RAG 闭环）。`human`（人工确认节点，配 `approvals`）**为 Backlog**（SD-17）。

- 每个节点的 `input_template` / `arguments_template` 用 **受限表达式**（`{{state.x}}`、`{{nodes.search.output}}`、以及 `len(...)` 等只读函数），由 `workflow/template.py` 求值，**禁止 `eval`**。

### 2.14 迁移策略

- **唯一通道**：Alembic。`app/db/base.py` 的 `Base.metadata` 只作为 autogenerate 的输入，**任何环境都不调用 `create_all()`**（测试用 `alembic upgrade head` 对临时库执行，保证迁移脚本本身被测到）。
- 迁移脚本命名：`{revision}_phase{N}_{slug}.py`，例如 `0006_phase5_knowledge_tables.py`，让"数据模型随 Phase 增长"这一事实在版本历史里可见。
- 内置工具与三个 Demo Agent 的初始化走**数据迁移**（`op.bulk_insert`），不用 `seed` 脚本，保证 `alembic upgrade head` 一步到位可运行。
- **数据库范围（SD-8）**：只保证 SQLite 正确。迁移脚本不做 PG 兼容性验证（不写 `asyncpg`、不在 CI 跑 PG）；`database_url` 仍可配置，仅为"不锁死"保留可能性。
- 跨库注意（**当前不验证，仅记录**）：SQLite 用 `batch_alter_table`（`render_as_batch=True`）以支持加约束；`JSON` → `JSONB` 的差异在 `env.py` 中按 `database_url` 方言注册类型装饰器。
- 回滚：每个 Phase 的迁移必须提供 `downgrade()`；`Phase 8` 前不允许出现"删表型"破坏性迁移（保持"可演示"）。
- **数据目录自愈**：`DATABASE_URL` 默认指向 `./data/app.db`，而 `data/` 在 `.gitignore` 里——干净检出（CI、新克隆、挂到空卷的容器）时目录并不存在，SQLite 会直接抛 `unable to open database file`。`app/db/session.py::ensure_sqlite_directory()` 在**建 engine 之前**统一补齐父目录，`alembic/env.py` 与 `get_engine()` 共用同一实现，保证"配置里写了哪个路径就一定跑得起来"；`:memory:`、`file:` URI 与非 SQLite（SD-8）一律跳过。

## 3. API 契约

### 3.1 通用约定

- **Base path**：`/api/v1`；健康检查在根路径（`/healthz`、`/readyz`）
- **文档**：`/openapi.json`、Swagger UI `/docs`（`prod` 可用 `ENABLE_DOCS=false` 关闭）
- **成功响应**：`{ "data": …, "meta": { request_id, trace_id, page, page_size, total } }`；`page*` / `total` 仅列表接口出现
- **游标分页的返回**：`messages` / `traces` 两个接口额外返回 `meta.next_cursor`（不透明字符串，为空 = 没有更多；请求时原样回传 `?cursor=`）
- **错误响应**：见 1.6，HTTP 状态码随 `AppError.http_status`
- **分页**：偏移分页 `?page=&page_size=`（默认 20，最大 100）用于配置类资源；游标分页 `?limit=&cursor=` 用于 `messages` / `spans` / `traces`
- **排序 / 过滤**：`?sort=-created_at`（`-` 为降序）；过滤用显式命名参数，如 `?agent_id=&status=&q=`
- **时间格式**：统一 ISO 8601 UTC，如 `2026-09-29T12:00:00.123Z`
- **幂等**：写接口支持 `Idempotency-Key` 头（见 1.5.5）
- **鉴权**：**不实现**（SD-3）；`owner_key` 固定 `local`，`AUTH_*` 只存在于错误码表
- **长任务**：摄取 / 评测 / Workflow 运行为异步：`POST` 返回 `202` + 资源对象（`status=running`），前端轮询 `GET`（SSE 仅用于 Chat 流，见 3.4）
- **取消**：统一 `POST /runs/{run_id}/cancel`、`POST /workflow-runs/{run_id}/cancel`

### 3.4 SSE 事件协议（Chat 流）

- 传输：`text/event-stream`；**每 15s 发一次 `heartbeat`** 防代理断开；客户端断开由服务端检测并 `cancel` Run（可配 `DETACH_CANCEL`，默认**不取消**，保证刷新页面后仍能续看历史）。
- 事件负载统一为 JSON（`data:` 单行，内部不含裸换行）；沿用 1.6 的错误体，但通过 `error` 事件推送而非 HTTP 状态码。
- **事件名是前后端唯一契约**（前端 `sse.ts` 按此分发），新增事件必须同时更新本表与附录 B。
- **MVP 实际会发出的 18 个事件**：3.4 表中标 `Backlog` 的 3 个（`approval.required`、`memory.recalled`、`memory.updated`）当前**不产生**；它们仍保留在 `SseEventType` 与附录 B 中，因为"事件名集合"是一份整体契约（前端类型、契约测试一次性对齐），单独删除会在迭代 C/A 时破坏兼容性 —— 这是 SD-14② 的**显式豁免**，已在 SD-17/SD-15 中登记。

| # | event | 阶段 | payload（关键字段） | 触发时机 |
|---|---|---|---|---|
| 1 | `run.started` | 1 | `run_id, trace_id, started_at` | Run 落库后 |

| 7 | `tool.call.completed` | 2 | `tool_name, status` | 工具执行成功 |
| 8 | `tool.call.failed` | 2 | `tool_name, error_code` | 失败 / 超时 / 被拒 |

## 4. 运行时详细设计

本章对应《设计大纲》的"总体架构"与"设计原则 2、3"：每个可替换件都有抽象接口 + 至少一个实现 + 一个测试替身（fake）。

### 4.1 LLM Provider

#### 4.1.1 接口定义

```python
@dataclass(frozen=True)
class ChatMessage:
    role: MessageRole                      # system | user | assistant | tool
    content: str = ""
    tool_calls: list[ToolCallSpec] = field(default_factory=list)   # assistant 发起
    tool_call_id: str | None = None        # role=tool 时必填
    name: str | None = None

@dataclass(frozen=True)
class ToolCallSpec:
    id: str
    name: str
    arguments: dict[str, Any]              # 已 json.loads；解析失败则 arguments={} 且 raw 保留

@dataclass
class LLMResult:
    message: ChatMessage
    finish_reason: str                     # stop | tool_calls | length | content_filter | error
    usage: TokenUsage                      # prompt/completion/total
    model_name: str
    latency_ms: int
    cost_usd: Decimal = Decimal("0")        # 4.8.3 估算；上游无价格 → 0（4.1.2 第 7 条）
    cost_estimated: bool = False            # 价格缺失 → false
    usage_estimated: bool = False           # 上游未回 usage、本地估算 → true（4.1.2 第 6 条）
    raw: dict | None = None                # 调试用，不入库（除 Trace 的 attributes 摘要）

class LLMProvider(Protocol):
    name: str

    async def chat(
        self,
        messages: list[ChatMessage],
        *,
        model: str,
        tools: list[ToolSpec] | None = None,
        params: dict[str, Any] | None = None,
        stream: bool = False,
        on_delta: Callable[[str], Awaitable[None]] | None = None,
        on_tool_call: Callable[[ToolCallSpec], Awaitable[None]] | None = None,
        trace_span: Span | None = None,
    ) -> LLMResult: ...

    async def embed(self, texts: list[str], *, model: str) -> list[list[float]]: ...
```

约定：

- **`chat` 是唯一对话入口**，流式与非流式共用；`stream=True` 时逐段调用 `on_delta`，同时**累积完整内容**后返回 `LLMResult`（保证调用方无需区分两条路径）。
- `tools` 由 `ToolRegistry` 生成（见 4.2.2），Provider **不关心工具来源**（落实大纲 Phase 6 的目标）。
- Provider 层不做重试（重试在 1.5.3 定义的装饰器上），但**必须**把 SDK 异常翻译为 `AppError`（`MODEL_*`）。

#### 4.1.2 OpenAI-compatible 实现要点

对应大纲「支持 OpenAI-compatible API」「模型接口需要进行统一封装，使后续能够切换不同模型」：

1. 依赖仅 `httpx.AsyncClient`（不自带 OpenAI SDK），避免各家兼容层差异；请求体严格遵循 OpenAI Chat Completions 规范（`/chat/completions`、`/embeddings`）。
2. `base_url` 归一化：自动补 `/v1` 与去尾斜杠；兼容 DashScope、DeepSeek、vLLM、Ollama（`http://localhost:11434/v1`）等。
3. 流式解析：按 `data: ` 分帧，处理 `[DONE]`；对 `delta.tool_calls` 做**增量拼接**（按 `index` 聚合 `id` / `function.name` / `function.arguments` 分片），最后一个 chunk 的 `finish_reason` 决定最终值。
4. `tool_choice="auto"` 为默认；`Agent.tool_ids` 为空时**不下发 `tools` 字段**（防止部分兼容实现报错）。
5. 参数透传白名单：`temperature top_p max_tokens stop presence_penalty frequency_penalty seed`；`model_params` 与 provider `default_params` 浅合并，Agent 优先。
6. Token 统计：优先取响应 `usage`；缺失时估算，并在 `spans.attributes.usage_estimated=true` 标注。
7. 成本估算：`model_providers.models[].input_price_per_1k_usd / output_price_per_1k_usd` × 用量；**价格缺失时 cost 记 0 并标 `cost_estimated=false`** —— 这是大纲 Phase 7 "LLM Cost（如果 API 提供）" 的落地方式。

#### 4.1.3 Registry 与测试替身

```python
class LLMRegistry:
    def __init__(self, settings: Settings) -> None:
        self._factories: dict[str, Callable[[ProviderConfig], LLMProvider]] = {
            "openai_compatible": OpenAICompatibleProvider,
            "fake": FakeLLMProvider,          # 仅 app_env == "test" 时注册
        }

    def create(self, config: ProviderConfig) -> LLMProvider: ...
```

> **入参是 `ProviderConfig`（不可变快照），不是 ORM 行**：`runtime/**` 按 1.2 禁止 import
> `db/models` / `services`，服务层负责把 `model_providers` 行 + 解密后的 `api_key` 装配成
> `runtime/llm/base.py::ProviderConfig`（文档 4.1.3 原文写作 `ModelProviderRow`，实现时按此收敛）。

`runtime/llm/fake.py` 的行为契约（Phase 1–7 的自动化测试大量依赖它，**必须稳定**）：

- 触发条件 → Fake 行为（判定依据是最后一条 user 消息）：
  - 含 `计算` / `calculate` 且工具含 `calculator` → 返回 `tool_calls=[calculator(...)]`，参数从文本中提取算式
  - 含 `检索` 且 Agent 绑定 KB → 返回 `tool_calls=[kb_search(...)]`
  - 第二轮（messages 中已存在 tool 消息）→ 直接 `finish_reason=stop`，内容为 `"结果：{tool 结果}"`
  - 其他 → 返回 `"FAKE_RESPONSE: {user 文本}"`，`usage = TokenUsage(10, 5)`
  - 参数含 `simulate_error=timeout` → 抛 `MODEL_TIMEOUT`

> **Phase 1 的两条实现约定**（代码与测试据此对齐，属 4.1.3 的细化）：
>
> 1. `simulate_error=<code>` 的识别位置有两个：`params`（`model_params` / provider `default_params`，优先级更高），以及**最后一条 user 消息的文本**（形如 `simulate_error=auth`）。后者让端到端测试不必改 Agent 配置即可覆盖 `MODEL_*` 各分支；`<code>` 取值 = `timeout | auth | bad_request | rate_limited | unavailable | context_overflow`。
> 2. `fake` 只作为**测试替身**存在：`ProviderKind`（0.2.2 A 段）不含它，因此 `POST /model-providers` 无法创建 `kind=fake`（422）；只有 `settings.app_env == "test"` 时 `services/model_provider_service.create()` 才接受它，供集成测试在库中造出一条 fake Provider（`tests/helpers.py::create_fake_provider`）。

配套：`EMBED_ALLOW_FAKE=true` 时 `FakeEmbeddingProvider` 用 `hash(text)` 生成 32 维确定性向量，使 RAG 测试无需真实 embedding 服务，且向量近邻关系可被断言。

### 4.2 Tool Runtime

对应大纲 Phase 2 的六项要求：`Tool Registry / Tool Schema / Tool Executor / Tool Permission / Tool Error Handling / Tool Call Trace`。

#### 4.2.1 内置工具接口

```python
class BaseTool(ABC):
    name: str                       # 与 tools.name 一致
    description: str
    input_schema: dict[str, Any]    # JSON Schema
    default_permission: ToolPermissionConfig

    @abstractmethod
    async def run(self, ctx: ToolContext, **kwargs: Any) -> ToolResult: ...

@dataclass
class ToolContext:
    run_id: str
    trace_span: Span
    sandbox_root: Path
    settings: Settings
    cancellation: asyncio.Event

@dataclass
class ToolResult:
    content: str | dict             # 回填给 LLM 的内容（会做 JSON 序列化）
    is_error: bool = False
    meta: dict[str, Any] = field(default_factory=dict)   # 合入 span.attributes
```

#### 4.2.2 Tool Registry 与 schema 生成

- 启动时（`lifespan`）扫描 `runtime/tools/builtin/` 中的 `BaseTool` 子类注册进内存 `ToolRegistry`，并**与数据库对齐**：缺失则插入（`is_system=true`），`description` / `input_schema` 变更以**代码为准**更新 DB —— 内置工具定义单一来源，避免"代码与库不一致"。
- 生成 LLM function schema（大纲 "Tool Schema"）：

```json
[{"type":"function","function":{"name":"calculator","description":"计算数学表达式",
   "parameters":{"type":"object",
     "properties":{"expression":{"type":"string","description":"要计算的表达式"}},
     "required":["expression"],"additionalProperties":false}}}]
```

- 工具可见性规则（写死）：仅下发 `Agent.tool_ids` ∩ `tools.status=enabled` ∩（`tool_type=mcp` 时其 Server `enabled=true`）的工具；**每一步都重新计算**，因此运行期间禁用工具会立即生效。

#### 4.2.3 Tool Executor 执行流水线

`ToolExecutor.execute(run, call: ToolCallSpec) -> ToolInvocationResult`，九步**顺序固定**，每步都有对应单测：

```text
1. 查表       → tool 存在？ status=enabled？ 否则 TOOL_NOT_FOUND / TOOL_DISABLED
                （MVP 不接受 tool_type=mcp：不存在 mcp_servers 时视为 VALIDATION_ERROR，明细 TOOL_TYPE_NOT_SUPPORTED）
2. 合并策略   → Agent 级与工具级 permission_config 取更严格者
3. 参数校验   → JSON Schema 校验 arguments，失败 → TOOL_INVALID_ARGUMENTS（错误回填给 LLM，不中断 Run）
4. 权限判定   → safe → allow；guarded → 校验 allowed_paths / allowed_hosts
                dangerous 或 require_approval=true 的工具未在 Settings 显式开启 → deny
                （TOOL_PERMISSION_DENIED，错误回填；MVP 不挂起、不建 approvals，SD-17）
5. 次数闸门   → 本 Run 内该工具调用数 > max_calls_per_run → TOOL_PERMISSION_DENIED
6. 执行       → 按 tool_type 分派：builtin / api(httpx)
                asyncio.wait_for(timeout) + 令牌桶限流
7. 输出处理   → 归一为 str|dict；超 max_output_bytes 截断（result_truncated=true）
                出错时构造 {"error": code, "message": ...} 作为**正常结果**回填
8. 落库       → tool_invocations 一行 + span 结束（arguments / result / latency / attempts）
9. 返回       → ToolInvocationResult（供 AgentRuntime 组装 tool 消息）
```

> Backlog 迭代 B 会把步骤 6 的 `mcp` 分派点接回（`MCPToolAdapter`），迭代 C 会把步骤 4 的 `deny` 改为"写 `approvals` + 挂起"；两处都是**局部改动**，不动其余 7 步。

**错误处理原则**（大纲 "Tool Error Handling"）：

- 工具失败**默认不中断 Run**（`RUN_CANCELED` 除外），把错误文本作为 `role=tool` 消息回填，让 LLM 自行修复或换工具；
- 同一工具连续失败 3 次 → Run 失败，`TOOL_REPEATED_FAILURE`；
- `TOOL_TIMEOUT` 时若为 `builtin` 且已 `kill` 子进程，仍会把"超时"信息回填；
- 所有失败都会写入 `tool_invocations.error_code` 与对应 span 的 `error_*`，不出现"静默失败"。

#### 4.2.4 沙箱（`runtime/tools/sandbox.py`）

- **路径校验**：`path.resolve()` 必须位于 `SANDBOX_ROOT` 或工具 `allowed_paths` 之下；拒绝符号链接逃逸；拒绝对绝对路径写入
- **目录创建**：`file_write` 仅在 `uploads/`、`outputs/` 下创建新文件
- **大小限制**：单文件读 ≤ 5 MB；写 ≤ 1 MB；`file_read` 支持 `offset/limit` 分段读
- **网络**：`web_search` / `api` 工具仅允许 `allowed_hosts`；禁止 `127.0.0.1` 与内网段（防 SSRF）
- **审计**：被拒绝的调用也写 `tool_invocations(status=failed, error_code=TOOL_SANDBOX_VIOLATION)` 并落 span，便于排查"Agent 试图越权"
- **`python_execute`**（默认禁用：`PYTHON_EXECUTE_ENABLED=false`；启用后四道闸门）：
  1. **AST 解析**：`import` / `from ... import` 只允许白名单模块（`math` `statistics` `json` `re` `datetime` `csv` `collections` `itertools` `decimal` …），并拒绝 `eval/exec/compile/__import__/open` 的越权形态；
  2. **子进程**：`asyncio.create_subprocess_exec(sys.executable, "-I", "-c", code)`，cwd 固定沙箱子目录，`env` 仅保留 `PATH/PYTHONIOENCODING`；
  3. **超时**：超时杀整个进程组（`AGENT_TOOL_TIMEOUT`）；
  4. **截断**：stdout / stderr 按 `TOOL_MAX_OUTPUT_BYTES` 截断。
  明确**不承诺网络隔离**（SD-4）。

> **明确局限（写进 README 的"已知限制"）**：`python_execute` 的隔离 = 子进程 + AST 白名单 + 路径限制，**不是安全边界**（Python 层面存在绕过手法），仅为"演示工程链路 + 拦住明显误用"而设计（SD-4）。禁止把它描述成"沙箱安全"；真实场景需容器 / 微虚拟机 / WASM（当前明确不做，见 0.4.2）。

### 4.3 Memory Runtime（MVP：仅 4.3.1 短期记忆；4.3.2/4.3.3 为 **Backlog**，SD-15）

对应大纲 Phase 4：「Short-term Memory 保存当前 Conversation / Workflow 状态」「Long-term Memory 允许 Agent 保存和检索跨 Session 信息」，且需考虑 `Memory Storage / Retrieval / Update / 生命周期`。

> **MVP 停止线**：只实现**短期记忆 = 上下文窗口装配**（4.3.1 的 `window` 策略）；`summary` 策略、长期记忆（4.3.2）、以及 `MemoryBackend` 的记忆语义（4.3.3）都在迭代 A。选择"窗口装配"作为最小实现的理由：它**不新增任何表与配置项**，却已经决定了 Agent 的上下文质量（成对裁剪、token 预算），是面试里能讲清楚的设计点。

#### 4.3.1 短期记忆（无独立存储）

短期记忆 = **上下文窗口装配策略**，直接从 `messages` 读取（唯一事实来源）：

```python
class ShortTermMemory(Protocol):
    async def build(self, conversation_id: str, *, agent: AgentSpec) -> list[ChatMessage]: ...
    async def append(self, conversation_id: str, message: ChatMessage) -> None: ...
```

> **Phase 1 的三处签名细化**（实现需要，语义不变）：
>
> - `append(conversation_id, message, *, run_id=None) -> str`：返回新行的 `message_id`，
>   供 `message.started` / `message.delta` 携带**稳定 id**（3.4 事件 3/4）；
> - `complete(message_id, *, content, finish_reason, usage, latency_ms, model_name, error_code=None) -> None`：
>   流式结束后回填那行 assistant 消息（先落空内容行，崩溃时也能看到"进行中的消息"）；
> - `build(..., before_seq: int | None = None)`：只取 `seq < before_seq` 的历史，
>   这样 4.4.2 的装配顺序（system → 短期窗口 → **本次 user 消息**）不会重复计入本轮 user 消息。

- **`window`（MVP 唯一实现）**：取最近 `max_turns` 轮（一轮 = user + 其后所有 assistant/tool 消息），再按 `max_tokens` 从后往前裁剪；**裁剪必须成对保留** `assistant(tool_calls)` 与其 `tool(tool_call_id)`，否则部分模型会 400
- **`summary`（Backlog）**：超过 `summarize_threshold_tokens` 时，把更早的消息交给 LLM 生成摘要（存为 `memory_items(kind=summary, scope=session)`），上下文 = `system + 摘要 + 最近 max_turns 轮`
- **`window+summary`（Backlog）**：两者结合 —— 近端窗口 + 远端摘要


**Workflow 状态**是短期记忆的另一种形态：`workflow_runs.state` 即"当前 Workflow 的内存"，节点间通过 state 传递（见 4.5.2），不写入 `messages`。

#### 4.3.2 长期记忆（**Backlog**，SD-15：迭代 A 实现）

> 以下设计**不在 MVP 的代码范围内**，保留原文是为了迭代 A 可直接照此实现（`LongTermMemory`、`memory_items`、`memory_write` 的接管点已定）。

```python
class LongTermMemory(Protocol):
    async def recall(self, query: str, *, scope: MemoryScope, scope_key: str,
                     top_k: int, min_score: float) -> list[MemoryItem]: ...
    async def write(self, items: Iterable[MemoryCandidate], *,
                    scope: MemoryScope, scope_key: str, source_run_id: str) -> WriteOutcome: ...
```

- **存储**：向量（`vectorstores` 的 `mem_{scope}` collection）+ 元数据（`memory_items` 表）；`vector_id = memory_items.id`。
- **检索（recall）**：以最近一条用户消息为 query → 余弦 top_k → 过滤 `status=active`、`score >= min_score`、未过期 → 按 `score * (0.7 + 0.3 * importance)` 重排 → 返回前 `retrieve_top_k` 条；命中后 `hits += 1`、更新 `last_accessed_at`。
- **写入（write）**：`write_policy` 三种取值
  - `off`：不写（默认）；
  - `explicit`：仅当模型调用内置工具 `memory_write`（Phase 4 注册的"隐藏工具"，不在 UI 工具列表中，随 `memory_config.long_term.enabled` 自动附加）时才写；
  - `auto`：Run 结束后用一次 LLM 抽取"值得长期记住的事实/偏好"（严格 JSON 输出 schema），**上限 3 条**，`importance < 0.4` 丢弃。
- **去重/更新**：写入前对同一 `scope+scope_key` 做相似度检索，若已存在 `score > 0.92` 的记忆则走**更新**（覆盖 content、取 `max(importance)`、合并 `source_message_ids`），否则新增；避免"每次对话都新增一条同义记忆"。
- **生命周期**：`ttl_seconds` 到期 → `status=expired`；删除记忆同时删向量；每 Scope 上限默认 500 条，超出按 `importance asc, last_accessed_at asc` 淘汰。
- **可见性**：Chat 页展示本次 Run 的 `memory.recalled` / `memory.updated` 事件（3.4 事件 11/12），让"Agent 记得什么"可解释 —— 这是 Phase 4 的演示重点。

#### 4.3.3 Provider 抽象与替换（`VectorStore` 本身在 MVP 有用；记忆语义为 Backlog）

`MemoryBackend` 把"向量后端"与"记忆语义"分开。**MVP 中这套 Protocol 由 RAG 使用**（`rag/retriever.py` 通过它读写 `kb_{kb_id}` 集合），因此接口在 MVP 就要定好；只有"记忆语义"（`LongTermMemory`）属于迭代 A。

```python
class MemoryBackend(Protocol):        # 由 vectorstores 实现（chroma / memory，SD-11）
    async def upsert(self, collection: str, items: list[VectorItem]) -> None: ...
    async def query(self, collection: str, vector: list[float], top_k: int) -> list[VectorHit]: ...
    async def delete(self, collection: str, ids: list[str]) -> None: ...
```

→ 满足大纲原则 3："Memory Backend 通过接口抽象"；切换向量库不需要改 `LongTermMemory` 一行代码。

### 4.4 Agent Runtime

平台的核心循环，对应大纲 Phase 1（最小 Runtime）与 Phase 2（Tool Calling）的叠加。

#### 4.4.1 状态与接口

```python
@dataclass
class AgentState:
    run_id: str
    trace_id: str
    agent: AgentSpec                # 配置快照（prompt_version、model、tool_ids、kb_ids、memory_config）
    conversation_id: str | None
    messages: list[ChatMessage]     # 装配后的上下文（发给 LLM 的）
    step_index: int = 0
    usage: TokenUsage = ZERO
    tool_call_count: int = 0
    recent_tool_failures: dict[str, int] = field(default_factory=dict)
    finish_reason: str | None = None
    error: AppError | None = None
    started_at: datetime = now_utc()

class AgentRuntime:
    async def run(self, agent: AgentSpec, user_input: str, *,
                  conversation_id: str | None = None,
                  emit: EventEmitter,                    # SSE 回调（无 SSE 时用 NullEmitter）
                  cancel: asyncio.Event) -> RunResult: ...
```

`emit` 与 `cancel` 用注入方式传入，使同一个 `AgentRuntime` 既能服务 HTTP/SSE，也能被 `WorkflowEngine`、`EvalRunner`、`scripts/evaluate.py` 复用（不依赖 Web 框架，符合大纲原则 2）。

#### 4.4.2 上下文装配顺序（写死）

```text
1. system 消息 = agent.system_prompt
               + [Phase 5] "以下是知识库检索结果，回答时请引用来源：\n<chunk ...>"
               + [Backlog/Phase 4] "以下是关于用户的长期记忆：\n- ..."   ← MVP 不注入（SD-15）
2. 短期记忆    = ShortTermMemory.build()   （window 策略，4.3.1）
3. 本次 user 消息（已落库）
4. 循环中的 assistant(tool_calls) 与 tool 消息（按 step 追加）
```

- 检索与（Backlog 的）记忆召回在**第一次 LLM 调用之前**执行一次；检索有两种模式，都保留：`agent.knowledge_base_ids` 非空 → 固定预检索（把结果放进 system，适合"知识助手"）；未绑定 → 由 `kb_search` 工具按需检索（适合"研究助手"）。两种模式的配置见 8.1。
- 每一步都**重新组装**上下文（工具结果进入 messages），历史消息本身不被修改，保证可重放。
- **MVP 的上下文装配只有 system + 短期窗口 + 本轮消息**（无长期记忆注入）——这一点在 README 的"已知限制"里如实写明。

#### 4.4.3 主循环与停止条件

```text
while step_index < agent.max_steps:
    step_index += 1; emit(agent.step.started)
    result = llm.chat(messages, tools=visible_tools(), stream=..., on_delta=emit_message_delta)
    累加 usage; emit(message.completed) / emit(usage.updated)
    if result.finish_reason == "tool_calls":
        for call in result.tool_calls:              # 顺序执行（SD-2：不实现并行）
            inv = tool_executor.execute(call)       # 被拒/失败都作为结果回填，不挂起（SD-17）
            messages += [assistant(tool_calls), tool(inv)]   # 落库
        continue
    emit(message.completed); break
else:
    → Run 失败 MODEL_MAX_STEPS_EXCEEDED
```

停止/终止条件汇总（每种都写 `runs.status` 与 `error_code`）：

- `finish_reason=stop` 且无 tool_calls → `succeeded`
- `step_index` 达 `max_steps` → `failed` / `MODEL_MAX_STEPS_EXCEEDED`
- 时长超 `agent.timeout_seconds` → `failed` / `RUN_TIMEOUT`
- 用户取消（`cancel` 置位）→ `canceled` / `RUN_CANCELED`
- LLM 错误且重试耗尽 → `failed` / `MODEL_*`
- 同一工具连续失败 3 次 → `failed` / `TOOL_REPEATED_FAILURE`
- 工具需审批但未开启 → 该次调用被拒并回填，Run 继续（SD-17；迭代 C 才改为挂起）

#### 4.4.4 与 Workflow 的关系（早期决策，避免 Phase 3 返工）

**Agent 是 Workflow 的一种节点类型**（`node.type=agent`），不是两套并行运行时：

- `Agent.workflow_id` 为空 → 直接跑 `AgentRuntime`（Phase 1/2 行为，Chat 页使用）；
- `Agent.workflow_id` 非空 → 由 `WorkflowEngine` 驱动该图，其中每个 `agent` 节点内部**复用同一个 `AgentRuntime.run()`**，把节点输出写入 state；
- 因此 Chat 页在 Workflow 模式下也能显示 `workflow.node.*` 事件（3.4 事件 13/14），Trace 树天然统一：`run → workflow → node → agent → llm/tool`。

### 4.5 Workflow Engine

对应大纲 Phase 3：从"对话循环"扩展为可编排 Workflow，先支持 JSON/Python 配置，**不做可视化编辑器**。

#### 4.5.1 接口与实现策略

```python
class WorkflowEngine(Protocol):
    async def run(self, graph: WorkflowGraph, initial_state: dict[str, Any], *,
                  run_id: str, emit: EventEmitter, cancel: asyncio.Event) -> WorkflowResult: ...
    async def resume(self, checkpoint: dict[str, Any], *,
                     run_id: str, emit: EventEmitter, cancel: asyncio.Event) -> WorkflowResult: ...
```

- `workflow/graph.py` 把 `definition` JSON 解析为 `WorkflowGraph`（节点、出边、校验结果），并做**静态校验**：节点 id 唯一、恰好一个 `start`、至少一个 `end`、所有 `next`/`branch.next` 可达、无孤立节点、`agent` 节点引用的 Agent 存在、**任一节点出边数 ≤ 1（SD-1）**。校验失败 → `WORKFLOW_INVALID_GRAPH`（422，错误清单在 `details.errors`，其中并行出边的单项 `code=PARALLEL_EDGES_NOT_SUPPORTED`）。
- **引擎实现（SD-10）**：Phase 3 只实现一个 —— `SimpleEngine`（纯 `asyncio`，自己维护 ready 队列 + 循环上限）。它零第三方依赖、语义完全可见、好写单测，是"先把图语义做对"的路径。
- **不为"可替换"提前写第二套实现**（SD-14 红线①）：`WorkflowEngine` Protocol 与 `tests/unit/workflow/test_engine_contract.py`（conformance 模板）保留，但模板当前**只参数化 `SimpleEngine`**。将来若要加 `LangGraphEngine`（可选加分项），前置条件是：① 该测试文件先扩成参数化两实现；② checkpoint 里写 `engine` / `engine_version`，`resume` 遇版本不匹配时降级为从头重跑。**加入第二个引擎不是任何 Phase 的 DoD。**

#### 4.5.2 节点类型与执行语义

| 节点类型 | 输入 | 输出（写入 state） | 失败处理 |
|---|---|---|---|
| `start` | `workflow_runs.input` | 原样进入 state | — |
| `agent` | `input_template` | `output_key` ← Agent 的最终回答 | 按 `on_error` 处理 |
| `tool` | `arguments_template` | `output_key` ← 工具结果 | 默认 `continue` |
| `retriever` | `query_template` + `kb_id` | `output_key` ← `RetrievedChunk[]` | 默认 `continue` |
| `condition` | `branches[].when` | 无（只决定跳转） | 求值异常 → 节点失败 |
| `human` | `payload_template` | 审批通过则继续 | **Backlog**（SD-17） |
| `end` | — | state 写入 `workflow_runs.output` | — |

- `on_error` 取 `fail` / `continue` / `retry(n)`（节点级配置；`agent` 默认 `fail`，`tool` / `retriever` 默认 `continue`）；`condition` 求值异常时抛 `WORKFLOW_NODE_FAILED`。
- `tool` 节点默认把错误文本写入 state，交给后续 `agent` 节点自行处理。

- **state 是单一字典**，约定命名空间：`state.<业务字段>`（用户输入与节点产物）、`nodes.<node_id>.output`（只读访问任一节点输出）、`run.<run_id>`。写冲突以"后写覆盖 + `node_runs` 保留历史"处理。
- **模板求值**：`workflow/template.py` 仅支持 `{{path.to.value}}` 与白名单只读函数（`len`、`str`、`join`、`json.dumps`），**不使用 `eval`/`exec`**；未定义字段 → 空串并记一条 warning 到 span attributes。
- **循环**：通过 `condition` 回边实现，受 `definition.config.max_steps`（默认 30）与 `recursion_limit`（默认 50）双重限制；超限 → `WORKFLOW_MAX_STEPS_EXCEEDED`。
- **并发（SD-1）**：节点**串行**执行。图校验阶段就拒绝并行：一个非 `branch` 节点只允许一条出边（`next`），`branch` 节点每路只能指向一个目标，出现"多条无条件出边"→ `WORKFLOW_INVALID_GRAPH`（422，错误项 `code=PARALLEL_EDGES_NOT_SUPPORTED`）。这样"不支持并行"是一条**可测试的校验规则**，而不是一句口头约定。

#### 4.5.3 事件与落库

每进入/离开一个节点：`workflow.node.started` / `workflow.node.completed`（3.4 事件 13/14）+ `node_runs` 一行 + 对应 span（`span_type=node`，父 span 为 workflow span）。`workflow_runs.state` 与 `current_node_id` **在每个节点结束时更新**，使前端即便轮询也能看到进度。

#### 4.5.4 Checkpoint / Resume（人工审批为 **Backlog**，SD-17）

- 每个节点结束后把引擎快照序列化进 `workflow_runs.checkpoint`：`{"engine":"simple","engine_version":"1","state":{...},"current_node_id":"...","pending_branch":null}`（SD-10：当前只有 `simple` 一种引擎，字段按"未来可加第二实现"设计）。
- `POST /workflow-runs/{id}/resume` 的**两种**合法场景（其余返回 `WORKFLOW_RUN_NOT_RESUMABLE` / 409）：
  1. `status=failed` 且失败原因属于可重试类（`MODEL_RATE_LIMITED`、`MODEL_TIMEOUT`、`TOOL_TIMEOUT`、`KB_EMPTY_INDEX`）；
  2. `status=running` 但进程曾重启（"孤儿 Run"），且 `current_node_id` 存在。
- **Backlog（迭代 C）**：补上第 3 种场景 —— `human` 节点或工具审批挂起中（`approvals(kind=node|tool_call)` → `approve` 从 checkpoint 续跑该节点，`reject` 按节点配置 `goto`/`end`，拒绝原因写入 `state.__rejected__`）。MVP 不含 `human` 节点与审批表，故不存在这一类挂起状态。

### 4.6 RAG 管线

对应大纲 Phase 5：`Document → Loader → Chunk → Embedding → Vector DB → Retriever → Agent`。

#### 4.6.1 各环节契约

| 环节 | 接口 | MVP 实现 | 关键参数 |
|---|---|---|---|
| Loader | `Loader.load(source)` | `TextLoader` / `MarkdownLoader` | 单文件 ≤ 10 MB |
| Splitter | `Splitter.split(doc)` | `Recursive` / `Markdown` | 800 / 120 overlap |
| Embedder | `Embedder.embed(texts)` | `OpenAICompat` / `Fake` | 批 32 条，重试 2 次 |
| VectorStore | 与 4.3.3 同构 | `Chroma` / `InMemory` | `kb_{id}` |
| Retriever | `Retriever.retrieve(...)` | 向量检索（多 KB → 重排） | `top_k=5`、`0.3` |
| Rerank | `Reranker.rerank(...)` | **Backlog** | `rerank_enabled=false` |

- 表中简写的实现类全称：`TextLoader` / `MarkdownLoader`、`RecursiveSplitter` / `MarkdownSplitter`、`OpenAICompatibleEmbedder` / `FakeEmbedder`、`ChromaVectorStore` / `InMemoryVectorStore`（后两个即 4.3.3 的 VectorStore 家族）。

- `Document = {text, meta}`；`MarkdownLoader` 保留标题层级到 meta，`TextLoader` 做编码探测；`RecursiveSplitter` 默认分隔符 `\n\n → \n → 。！？ → .`（带 overlap）；`Retriever.retrieve(...)` 返回 `RetrievedChunk[]`；`ChromaVectorStore` 本地持久化 `data/chroma`；`QdrantVectorStore` **不实现**（SD-11）。
- **Backlog（迭代 E）**：`PdfLoader`（pypdf，按页 `meta.page`，≤ 200 页）、`WebLoader`（httpx + 简易正文抽取）、`TokenSplitter`、`Reranker`（LLM 打分或 `bge-reranker` HTTP 服务）。

#### 4.6.2 摄取流水线（异步、可观测）

`POST /knowledge-bases/{id}/documents` → 返回 `202` + `documents(status=pending)` → 进程内 `TaskRunner`（`asyncio.Queue` + 单并发 worker，Phase 5 不引入 Celery）执行：

```text
pending → parsing → chunking → embedding → ready
                     ↘ 任一步失败 → failed（记录 error_code / error_message，可 reingest）
```

- 每个阶段写一条 span（`span_type=embedding` / 无独立 span 的解析阶段用 `attributes`），使 KB 页面（M3）能显示"每个文档的摄取耗时与失败点"。
- **幂等**：同 KB 内 `checksum` 相同的文档直接复用（`status=ready`，`chunk_count` 沿用），避免重复付费调用 embedding。
- **进度**：`documents.status` 变化即 GET 可见（前端 2s 轮询）；不做 SSE（理由同 Workflow：长任务需可刷新）。

#### 4.6.3 检索结果的使用与引用

- 命中结果注入 system（4.4.2 第 1 步），格式固定：

```text
[1] source=install.md#2.1 page=2 score=0.83
    内容片段…
```

- 回答中要求模型以 `[1]` 形式引用；`retrieval.completed` 事件把 `chunks[]` 摘要推给前端，Chat 页在回答下方渲染"引用来源"卡片（这是 RAG 可解释性的验收点）。
- **无命中**（`hit_count=0`）时**不注入空段落**，而是在 system 追加一句"当前知识库未检索到相关内容，请明确说明"——避免模型凭空编造。

### 4.7 MCP 集成（**Backlog**，SD-16：MVP 不实现）

> 本节设计完整保留：迭代 B 实现时只需新建 `runtime/mcp/` 与 `MCPToolAdapter`，并把它挂到 4.2.3 步骤 6 的 `mcp` 分派点。<br>
> MVP 的替代做法：需要"外部能力"时用 `tool_type=api`（声明式 HTTP 工具）+ 内置工具，同样能演示"工具来源可扩展"这一点。

对应大纲 Phase 6：**不重新实现 MCP 协议**，只把 MCP Server 的工具接入统一 Tool Registry，使"Agent 不需要知道 Tool 的具体来源"。

#### 4.7.1 客户端与传输

```python
class MCPClient(Protocol):
    async def connect(self) -> MCPHandshake: ...            # 返回 server_info + capabilities
    async def list_tools(self) -> list[MCPToolDef]: ...
    async def call_tool(self, name: str, arguments: dict) -> MCPToolResult: ...
    async def close(self) -> None: ...
```

- 传输：`stdio`（`asyncio.create_subprocess_exec` 启动子进程，走 stdin/stdout 的 JSON-RPC）、`sse`、`streamable_http`；三者共用 `transports/` 下的读写循环，仅"管道"不同。
- 会话生命周期：`MCPClientPool` 按 `mcp_servers.id` 缓存连接（空闲 5 分钟回收）；连接失败即标记 `status=error` 并记录 `last_error`，**不阻塞其他工具**。
- 依赖（**Backlog**）：`mcp` Python SDK 与 `MCP_TRANSPORT_ENABLED` 开关都属于迭代 B；MVP 不安装该依赖、不注册相关路由（SD-14②/16），`/api/v1/meta.features.mcp` 恒为 `false`。

#### 4.7.2 接入 Registry 的映射规则

```text
MCP tools/list → mcp_tools（原始定义）
              → tools（平台侧工具行）：tool_type="mcp",
                 name={tool_prefix}_{mcp_tool_name},
                 description=<原描述 + "(来自 MCP Server xxx)">,
                 input_schema=<直通>,
                 permission_config={level:"guarded", allow_network:true, timeout_seconds:30}
```

- 默认权限为 **guarded**（外部工具不可信），且 `allow_network=true` 仅针对该 Server 的 `url`/`command` 目标；MCP 工具**不支持** `require_approval=false` 覆盖成 safe。
- 调用链：`ToolExecutor` → `MCPToolAdapter.run()` → `MCPClient.call_tool()` → 结果转 `ToolResult`；整条链是一条 `span_type=mcp` 的 span（父为 tool span），因此 Trace 页能看到"MCP 往返耗时"。
- 工具名冲突：`tools.name` 唯一约束 + `tool_prefix` 强制非空（默认取 Server 名 kebab 化），冲突时 `sync` 返回 `CONFLICT` 并提示改名。

### 4.8 Trace / Observability / 成本

对应大纲 Phase 7 与「Execution Trace」表；实现落在 `runtime/observability/`，被所有模块复用（1.5.2 已定义上下文传播）。

#### 4.8.1 Span 树约定（固定层级）

```text
run            (span_type=run)                      ← Tracer.start_run
├── agent      (span_type=agent, name=agent:{name})
│   ├── memory (span_type=memory, name=memory:recall)        [Phase 4]
│   ├── retriever (span_type=retriever, name=kb:{kb_name})   [Phase 5]
│   ├── llm    (span_type=llm, name=llm:{model})             [每 step 一次]
│   ├── tool   (span_type=tool, name=tool:{tool_name})
│   │   └── mcp(span_type=mcp, name=mcp:{server}.{tool})     [Phase 6]
│   └── memory (span_type=memory, name=memory:write)         [Phase 4]
└── workflow   (span_type=workflow)                          [Phase 3，与 agent 同级]
    └── node   (span_type=node, name=node:{node_id})
```

`seq` 由 `Tracer` 在单一 Run 内自增分配（进程内计数器 + 落库校验），保证前端排序稳定。

#### 4.8.2 API 与写入策略

- `Tracer.start_run(kind, name, run_id, attributes) -> RunTrace`；`with tracer.span(...)` 自动处理异常 → `status=error` + `error_code`。
- 每个 span 结束时**立即写库**（1 次 INSERT）；写库失败**不影响主流程**（记 warning 日志，`spans` 与 `traces` 属于可观测副产物）。
- 截断：`input`/`output` 序列化后超 `trace_max_payload_bytes`（默认 8 KB）→ 只保留前 N 字节并写 `{"truncated": true, "original_bytes": n}`；`messages` 全量仍在业务表里，Trace 只做"摘要视图"。
- 脱敏：写入前过一遍 secret 过滤器（与日志同一实现），避免 API Key 落进 Trace。

#### 4.8.3 成本与聚合

- `cost.py`：`estimate_cost(model, prompt_tokens, completion_tokens, prices) -> Decimal`；价格为 `model_providers.models[]` 中配置。
- 单 span 记 `cost_usd` → `Tracer` 在 span 结束时把用量**向上累加**到父 span 与 `traces`；`runs` 与 `eval_results` 同步写入汇总值。
- `GET /stats/overview` 直接聚合 `runs` / `traces` 表（SQLite 下用 SQL 聚合即可；不引入时序库），返回大纲 Phase 7 所需的 `Success Rate / Average Latency / Average Tool Calls / Average Token Usage / Error Rate / Cost`。

### 4.9 Evaluation Framework（MVP：脚本 + 指标口径；DB 化评测台为 **Backlog**，SD-18）

对应大纲 Phase 7：「建立 Agent Evaluation Framework」+ 固定测试任务 + `python evaluate.py` + 报告输出。**MVP 只做这条命令行链路**（用例来自 YAML），四张 `eval_*` 表与评测页面见 2.12/3.2.10 的 Backlog 说明。

#### 4.9.1 Runner（MVP 形态）

```python
class EvalRunner:      # runtime/eval/runner.py —— 用例来源由 SuiteSource 决定
    async def run_suite(self, source: SuiteSource, *, agent_id: str,
                        concurrency: int = 2, emit: EventEmitter | None = None) -> EvalRunSummary: ...

class YamlSuiteSource(SuiteSource):   # MVP 实现：读 configs/eval/{name}.yaml
    ...
```

执行流程：

```text
1. 载入 YAML 用例集（name / agent / cases[].input / cases[].expected / cases[].weight）
   并把 agent 配置 + prompt_version 快照写进报告头（保证可复现）
2. 为每个 case 建 Run(kind="eval") + 独立 conversation（避免用例互相污染上下文）
3. 调 AgentRuntime（或 WorkflowEngine，当 agent.workflow_id 非空）
4. 收集产出：answer、tool_calls 序列、latency_ms、total_tokens、total_cost_usd、trace_id
5. 逐条断言（4.9.3）
6. 汇总 metrics（4.9.2），写 data/reports/eval-{ts}.md 与 .json（stdout 同时打印表格）
7. 全程受 max_concurrent_runs 与 eval_concurrency 双重限流；单 case 超时（默认 120s）记 outcome=error
```

- `scripts/evaluate.py` 只是 `YamlSuiteSource` + `EvalRunner` 的薄封装（解析 `--suite/--agent/--cases` 参数、退出码 = 是否存在 `failed`/`error`，便于 CI）。
- **Backlog（迭代 D）**：新增 `DbSuiteSource`（读 `eval_suites/eval_cases`）+ 结果落 `eval_runs/eval_results` + HTTP 入口。Runner、指标、断言、报告渲染**一行不改**。
- 每个 case 的 Run 仍落 `runs`/`spans`（`kind=eval`），所以"报告里某条没过 → 点开 `trace_id` 看完整链路"在 MVP 就可用。


#### 4.9.2 指标定义（写死，前端与报告共用）

| 指标 | 定义 |
|---|---|
| `task_success_rate` | 通过用例数 / 启用用例数（`llm_judge` 按 `score >= threshold`） |
| `tool_success_rate` | 成功 tool span / 全部 tool span（跨所有用例） |
| `workflow_success_rate` | `succeeded` / 全部 workflow_run（无用例时 `null`） |
| `avg_latency_ms` / `p95_latency_ms` | 用例级延迟的均值与 P95 |
| `avg_tool_calls` | 用例平均工具调用次数 |
| `avg_total_tokens` | 用例平均 token |
| `total_cost_usd` | 全批估算成本合计 |
| `error_rate` | `outcome=error` 占比（error = 执行异常，与 `failed` 区分） |

#### 4.9.3 断言实现

| type | 实现要点 |
|---|---|
| `contains` / `equals` / `regex` | 纯字符串处理；`equals` 支持 `normalize` |
| `json_path` | `json.loads` 后按简化 JSONPath（`$.a.b[0]`）取值比对 |
| `tool_sequence` | 比对工具调用名称序列（`in_order` / `exact` / `contains`） |
| `max_latency` | `latency_ms <= value_ms` |
| `llm_judge` | 调一次 LLM 按 rubric 打分（0~1 + 理由），`threshold` 判定 |

- `equals` 的 `normalize` 支持 `strip` / `lower` / `collapse_ws`；`tool_sequence` 的 `mode` 依次为"子序列 / 严格相等 / 包含"。
- `llm_judge` 由 `judges.py` 实现：judge 模型可在 eval_run 上覆盖（默认同 Agent 模型）；**judge 调用计入成本，但不作为 answer 断言**。

- 断言**全部执行、不短路**，`detail` 里保留每条结果 —— 便于"为什么没过"的定位（大纲"支持固定测试任务"的可调试性要求）。
- 断言失败不影响 Run 状态（Run 仍 `succeeded`），只有执行异常才 `error`。

#### 4.9.4 与工程流程的衔接

- CI（`ci.yml`）用 `FakeLLMProvider` 跑 **contract suite**（`configs/eval/contract-suite.yaml`，不依赖网络，断言"平台机制正确"：工具被调用、引用被注入、错误被回填）；
- 本地/发版用 `python scripts/evaluate.py --suite demo-suite --agent <id>` 跑**真实模型**评测，产出 `data/reports/*.md`，并把"最近一次结果"贴进 README（满足大纲"有 Evaluation Results"）；
- `data/reports/` 只保留最近 20 份（常量 `REPORT_KEEP` 定义在 `runtime/eval/report.py`，**不新增环境变量**），避免仓库噪音；**不做**自动清理 DB 与归档（SD-12/SD-18）。

### 6.1 服务拓扑（`docker/docker-compose.yml`）

```text
┌────────────┐     ┌──────────────┐     ┌────────────────────────┐
│  frontend  │────▶│   api        │────▶│  ./data/app.db (SQLite)│

```

| 服务 | 镜像/构建 | 端口 | 说明 |
|---|---|---|---|
| `api` | `backend/Dockerfile`（python:3.11-slim） | 8000 | 启动：迁移 + `uvicorn app.main:app` |
| `frontend` | `node:20` 构建 → `nginx:alpine` | 8080→80 | `/api` 反代到 `api:8000` |

- 依赖：`api` 用 `healthcheck: curl -f http://localhost:8000/readyz`；`frontend` `depends_on: api(condition: service_healthy)`。
- 演示用一条命令：`docker compose up --build`。
- 前端开发态不走容器：`npm run dev`（5173）由 Vite `server.proxy` 转发 `/api` 到 `localhost:8000`。

### 6.2 环境变量

全量清单见**附录 C**（`.env.example` 与该表逐项对应）。三层优先级：**进程环境变量 > `.env` > `Settings` 默认值**；`prod` 环境下 `secret_key` / `encryption_key` 仍为默认值时**启动即失败**（`CONFIG_INVALID`），避免上线裸奔。

### 6.3 启动自检与健康检查

`lifespan` 中的启动自检（任一失败则记录 ERROR 日志但**尽量不阻断启动**，除第 1 条）：

1. 迁移版本必须等于 head（不等 → 直接退出，防止 schema 漂移）；
2. 内置工具与 DB 对齐（4.2.2）；
3. 孤儿 Run / WorkflowRun 收敛：`status=running` 且 `started_at` 超 `timeout_seconds × 2` → 标 `failed` / `RUN_ABANDONED`；
4. 向量库可访问性（不可用 → `/readyz` 返回 503，`/healthz` 仍 ok）；
5. 生成 `GET /api/v1/meta` 的 `features` 快照（`mcp` / `eval` / `python_execute` 是否可用）。

| 探针 | 语义 |
|---|---|
| `GET /healthz` | 进程存活（不查依赖） |
| `GET /readyz` | DB 可写 + 迁移到 head + 向量库可达；失败返回 503 与具体原因 |
| `python -m app.scripts.check_readyz` | 与 `/readyz` 相同的检查项，但**不起 HTTP 服务**（CI 与容器内排查用；失败非 0 退出） |

> 说明：`DATABASE_URL` 指向的 SQLite 文件目录由 2.14 的 `ensure_sqlite_directory()` 在首次连库前自动创建，因此"干净检出 + 空卷"场景下 `alembic upgrade head` 与启动自检（第 1 条）都能直接通过。

### 6.4 CI（`.github/workflows/ci.yml`）

```text
job: backend  → ruff check + ruff format --check + mypy + pytest（含 alembic 往返测试）
                + 断言干净检出（rm -rf data && test ! -e data）
                + alembic upgrade/downgrade 往返 + 就绪探针（app.scripts.check_readyz）+ alembic check
job: frontend → eslint + tsc --noEmit + vitest + gen:api 一致性校验
job: docker   → docker compose build（不推送），验证镜像可构建
失败可读性: 所有 `run:` 经 `.github/scripts/tee_annotate.sh` 包装 —— 输出落盘到
          `$RUNNER_TEMP/<标签>.log`，失败时把尾部（换行转义为 `%0A`）写进 `::error::`
          **注解**与 job summary。注解在 `/commit/<sha>/checks` 页面**无需登录**即可读，
          而完整日志需要登录（公开仓库亦然）
调用形态: 门禁必须用控制台脚本 `pytest`（与 CI 完全一致）。`python -m pytest` 会把 CWD
          加进 `sys.path`，会掩盖 `from tests.* import ...` 这类导入问题 —— 2026-10-02 的
          事故正是如此（CI 退出码 2、本地却全绿），故 `pythonpath = ["."]` 是必需的（附录 F v1.8）
trigger: push / pull_request（不含 tag 的完整流水线最多 10 分钟）
```

## 8. 三个 Demo Agent 的配置清单

对齐大纲「开发三个不同类型的 Agent 验证通用性」：**类型差异只体现在 YAML 配置**，代码零分支（7.9 DoD 已把这一点列为硬性验收）。

### 8.1 配置文件格式与装载方式

`backend/configs/agents/{slug}.yaml` 的 schema（`AgentConfigFile`，Pydantic 强校验）：

```yaml
version: 1
agent:
  name: "Research Agent"
  description: "多步研究：规划 → 检索 → 撰写"
  is_template: true
  tags: ["demo", "research"]
  model:
    provider: "default-openai-compatible"   # 按 name 引用 model_providers
    name: "qwen-plus"
    params: { temperature: 0.3, max_tokens: 3000 }
  system_prompt: |
    你是一名严谨的研究员。回答问题时请遵循以下流程：
    1) 先判断是否需要检索（知识库优先，其次网络搜索）；
    2) 检索后必须给出引用编号，例如 [1]；
    3) 最终输出结构化报告：结论 / 依据 / 不确定项；
    4) 若证据不足，直接说明"未找到足够依据"，不要编造。
  tools: ["web_search", "calculator", "file_read", "kb_search"]
  knowledge_bases: ["product-docs"]         # 按 name 引用
  memory:
    short_term: { strategy: window, max_turns: 12, max_tokens: 6000 }
    long_term:  { enabled: false }
  workflow: "research-flow"                 # 可选，按 name 引用 workflows
  max_steps: 10
  timeout_seconds: 300
```

装载：`python -m app.scripts.seed_demo`（幂等，按 `name` upsert；`--reset` 会先删除同名 Agent）。同时提供数据迁移版本（`0009_phase8_demo_agents`）以便"迁移后即可演示"。

### 8.2 Demo 1：Research Agent（研究型）

- **依赖能力**：Workflow（Phase 3）+ Tool Calling（Phase 2）+ RAG（Phase 5）
- **Workflow**：`research-flow` = `start → planner(agent) → search(tool:web_search) → router(condition) → reader(retriever) → writer(agent) → end`
- **工具**：`web_search`、`calculator`、`file_read`、`kb_search`
- **Memory**：短期窗口（12 轮），长期关闭（研究过程不污染长期记忆）
- **展示目标**：多步编排、条件分支、工具调用、引用来源
- **体验问句**：「调研一下 2026 年国内主流向量数据库的差异，并给出选型建议」
- **边界（README 写明）**：不执行代码；不访问需要登录的站点；未命中知识库时明确说明

### 8.3 Demo 2：Data Analysis Agent（数据/代码型）

- **依赖能力**：Tool Calling（MVP，M2）+ RAG（MVP，M3）
- **工具**：`python_execute`（**默认禁用，需在 Settings 显式开启**）、`file_read`、`file_write`、`calculator`
- **Memory**：短期窗口（12 轮）；**无长期记忆**（长期记忆随迭代 A，SD-15）
- **Workflow**：无（直接 Agent 循环，证明"无 Workflow 也能用"）
- **展示目标**：**危险工具默认关闭 → 显式开启后可用**的开关式安全设计、代码执行沙箱、多轮数据追问
- **体验问句**：「读取 data/uploads/sales.csv，按月汇总销售额（输出表格即可）」→ 追问「把 3 月的异常点解释一下」
- **边界**：单文件 ≤ 1 MB；仅标准库；不使用网络（靠 AST `import` 白名单约束，**不是强制网络隔离**，SD-4）；`python_execute` 未开启时该次调用被拒（`TOOL_PERMISSION_DENIED`），LLM 会自动改用 `file_read` + `calculator` 完成简化任务

> 该 Agent 的存在价值：**证明平台能承载"需要执行代码"的类型**，同时把权限分级 + 沙箱两条安全链路演示完整（交互式审批属 Backlog 迭代 C：那时再加"人工批准"按钮）。


### 8.4 Demo 3：Knowledge Assistant（知识库问答型）

- **依赖能力**：RAG（MVP，M3，重点）+ Tool Calling（`kb_search`）
- **工具**：`kb_search`（若采用"固定预检索"模式则可无工具）、`calculator`
- **KB**：`product-docs`（装载 `tests/fixtures/docs/` 下的 md 示例，pdf 可选）
- **Memory**：短期窗口（12 轮）；**长期记忆 `scope=user` 随迭代 A**（那时体验"跨会话记住用户角色"）
- **Workflow**：无
- **展示目标**：文档摄取流水线、引用来源、拒答（无命中时不编造）、多轮追问
- **体验问句**：「我们产品的部署方式有哪些？」（引用若干 chunk）→ 追问「那第二种方式和第一种相比有什么代价？」
- **边界**：只回答知识库覆盖范围内的问题；过期文档需重新上传；**跨会话记忆是迭代 A 的能力，MVP 不做承诺**


### 8.5 通用性验收方法（可执行，不只是宣言）

| 检查 | 方法 | 通过标准 |
|---|---|---|
| 无专属代码 | `grep` 检索三个 Demo 名（命令见下） | 仅在 `configs/` 与文档中出现 |

| 评测覆盖 | `evaluate.py` 跑 contract + demo suite | contract-suite 成功率 = 100% |

> grep 命令：`grep -rn "Research Agent\|Data Analysis\|Knowledge Assistant" backend/app/`。
> `demo-suite`（真实模型）只记录**实测值**，不承诺 100%；`seed_demo` 幂等，`--reset` 会先删除同名 Agent。

## 9. 测试与质量门禁

### 9.1 分层与工具

| 层 | 范围 | 工具 | 运行时机 |
|---|---|---|---|
| 单测 `tests/unit/` | runtime 模块（无 DB / 网络） | pytest + pytest-asyncio | 每次提交（< 30s） |
| 契约 `unit/contract/` | 跨实现一致性（见下） | pytest 参数化 | 每次提交 |
| 集成 `integration/` | API + SQLite + Fake provider | pytest + `ASGITransport` | 每次提交（< 3min） |
| e2e `tests/e2e/` | 三个 Demo + 评测链路 | pytest | 每次提交 |
| live `@pytest.mark.live` | 真实模型（MCP 属 B 迭代） | pytest（默认排除） | 手动或 nightly |
| 前端 | 组件与 hook | vitest + Testing Library | 每次提交 |

- 表中"契约 / 集成"两行的完整目录是 `tests/unit/contract/` 与 `tests/integration/`。
- 契约测试覆盖：`LLMProvider`（`OpenAICompatible` + `Fake`）、`VectorStore`（`Chroma` + `InMemory`）、`WorkflowEngine`（**当前仅 `SimpleEngine`**，写成参数化形式，加实现时只追加参数）。
- 单测替身：`FakeLLMProvider` / `InMemoryVectorStore` / `FakeEmbedder`；文件类测试用 `tmp_path`。
- 集成测试用 httpx 的 `ASGITransport`（不启真实服务）；`live` 的默认参数是 `-m "not live"`。

### 9.2 测试替身的复用规则

- **所有测试禁止真实外网调用**（除 `live` 标记）：HTTP 用 `respx` 拦截；embedding 用 `FakeEmbedder`；`mcp` 的本地 stdio echo server 属迭代 B（SD-16）。
- `FakeLLMProvider` 的行为**只能通过消息内容驱动**（4.1.3），禁止在测试里 monkeypatch 它的内部方法 —— 否则契约测试失去意义。
- 时间相关逻辑（TTL、超时）用 `freezegun` 或注入 `clock` 参数，禁止 `time.sleep`。

### 9.3 覆盖率与质量门禁

| 门禁 | 阈值 | 说明 |
|---|---|---|
| `app/runtime/**` 行覆盖率 | ≥ 80% | 平台核心，必须有测试 |
| `app/services/**`、`app/api/**` | ≥ 70% | |
| 整体 | ≥ 70% | `coverage report --fail-under` |
| mypy | `app/runtime`、`app/core` 严格通过 | |
