## 一、项目定位

开发一个面向大语言模型 Agent 的轻量级、可扩展的 Agent 编排与执行平台。

平台的核心目标不是实现某一个固定场景的 Agent，而是提供一套通用机制，使用户能够通过配置模型、Prompt、Tools、Knowledge、Memory 和 Workflow，快速创建并运行不同类型的 Agent。

项目重点体现：

* LLM 应用开发
* Agent 架构设计
* Tool Calling
* Workflow 编排
* RAG
* Memory
* MCP
* Agent Evaluation
* Trace / Logging
* 前后端工程化

项目最终应当能够作为一个完整的开源项目运行，而不是单纯的 Demo。

> **定位补充（下位文档 0.4/0.5）**：本项目同时作为 Agent 开发求职/实习方向的学习与展示项目，**第一阶段（2–3 周）只承诺一条可演示的完整闭环**（Agent Runtime → Tool Calling → Workflow → RAG → Trace/评测脚本），**优先保证模块划分、接口设计与代码质量**，能力数量其次；明确"不做什么"（0.4.2 Non-Goals）并把"避免过早工程化"写成红线（SD-14）。

# 三、技术栈

## 后端

* Python
* FastAPI
* Pydantic
* AsyncIO
* SQLAlchemy

## Agent

优先使用 LangGraph 实现 Agent Runtime / Workflow。

> **下位文档收敛（SD-10）**：Phase 3 先只实现零依赖的自研 `SimpleEngine` + `WorkflowEngine` 协议，LangGraph 适配列为可选加分项（避免过早引入第二套实现）；协议保留，未来可加。

不要过度依赖框架内部抽象，核心 Agent 状态、Tool 调用和 Workflow 状态应该保持清晰。

## LLM

支持 OpenAI-compatible API。

第一阶段至少支持一种模型，例如：

* Qwen
* DeepSeek
* OpenAI-compatible local model

模型接口需要进行统一封装，使后续能够切换不同模型。

## RAG

第一阶段：

* Embedding
* Document Loader
* Chunking
* Retriever
* Vector Database

Vector DB 可以优先选择 Chroma 或 Qdrant。

> **下位文档收敛（SD-11）**：选 **Chroma**（进程内嵌、单目录持久化），只再补一个测试用的内存实现；Qdrant 不实现。

## 数据库

开发阶段可以使用 SQLite。

如果项目后续需要部署，再支持 PostgreSQL。

> **下位文档收敛（SD-8）**：**SQLite 为唯一目标数据库**，不引入 PostgreSQL；"可换库"只保留在 `DATABASE_URL` 配置项上，不排期、不测。

## 前端

React + TypeScript。

前端重点不是视觉效果，而是能够清晰展示：

* Agent
* Workflow
* Tool
* Conversation
* Execution Trace

## 部署

使用 Docker / Docker Compose。

# Phase 3：Workflow

将 Agent 从简单的“对话循环”扩展成可编排 Workflow。

支持：

```text
Start
 ↓
Agent
 ↓
Tool
 ↓
Agent
 ↓
Condition
 ├── True → Agent A
 └── False → Agent B
 ↓
End
```

第一阶段不需要做复杂的可视化 Workflow Editor。

> **下位文档沿用此取舍（SD-6）**：前端只做"JSON/YAML 编辑 + 校验提示 + 只读图渲染"，不做拖拽编辑器。

先使用 JSON / Python configuration 定义 Workflow。

例如：

```json
{
  "nodes": [
    {"id": "planner", "type": "agent"},
    {"id": "search", "type": "tool"},
    {"id": "writer", "type": "agent"}
  ]
}
```

目标：

> 能够构建多个节点组成的 Agent Workflow。

# Phase 4：Memory

> **下位文档收敛（SD-15）**：**整体延后到迭代 A**。第一阶段只做 **短期记忆**（= `messages` 的窗口装配，属 Phase 1 的上下文装配），不建 `memory_items` 表、不做向量记忆与自动抽取；本节设计原样保留，迭代 A 直接照此实现。

实现两种 Memory。

## Short-term Memory

保存当前 Conversation / Workflow 状态。

## Long-term Memory

允许 Agent 保存和检索跨 Session 信息。

例如：

```text
User
 ↓
Agent
 ↓
Memory Retrieval
 ↓
LLM
 ↓
Memory Update
```

需要考虑：

* Memory Storage
* Memory Retrieval
* Memory Update
* Memory 生命周期

目标：

> Agent 能够跨对话保留必要的信息。

# Phase 6：MCP

> **下位文档收敛（SD-16）**：**整体延后到迭代 B**（含 stdio 最小实现）。第一阶段的"统一 Tool Registry"由 `builtin` + `api` 两类来源证明；`ToolType.mcp`、`ToolExecutor` 的 mcp 分派点与 4.7 的设计已就位，接管点只有 `MCPToolAdapter` 一处。

加入 MCP Tool 支持。

目标不是自己重新实现完整 MCP 协议，而是：

> 将 MCP Server 提供的工具统一接入平台的 Tool Registry。

最终形成：

```text
Built-in Tools
       │
       ├────────┐
       │        │
       ▼        ▼
    Tool Registry
       │
       ├── Local Tool
       ├── API Tool
       └── MCP Tool
```

这样 Agent 不需要知道 Tool 的具体来源。

# 七、项目的核心设计原则

## 1. 不要做成“大而全”

优先保证：

> Agent → Tool → Workflow → RAG → Memory → Evaluation

这条链完整可运行。

> **下位文档收敛（SD-13/SD-15～SD-19）**：第一阶段（2–3 周 MVP）把这条链**收窄为** `Agent Runtime → Tool Calling → Workflow → RAG → Trace/评测（脚本）`，其中 **Memory 只做短期窗口**（长期记忆 = 迭代 A）；"整条链"在 Backlog 迭代 A–E 全部完成后达成。停止线、砍单顺序与演示脚本见下位文档 0.5。

---

## 2. 不要过度依赖第三方 Agent Framework

LangGraph 可以负责 Workflow，但：

> **下位文档收敛（SD-10）**：当前连 Workflow 也先由自研 `SimpleEngine` 承担（零依赖、可单测），LangGraph 只在"需要展示框架集成"时作为可选加分项加入；以下各项本来就自己设计，不受影响。

* Tool Registry
* Agent Configuration
* Memory
* Trace
* Evaluation

尽量自己设计。

这样才能体现工程能力。

---

## 3. 所有核心模块保持可替换

例如：

```text
LLM Provider
Embedding Model
Vector DB
Memory Backend
Tool Provider
```

都应该通过接口抽象。

例如：

```python
class LLMProvider:
    async def generate(...):
        pass
```

而不是在业务代码中直接大量调用具体模型 SDK。

---

## 4. 优先保证可测试性

核心 Agent Runtime、Tool Runtime、Workflow Engine、RAG、Memory 都应该有测试。

# 八、最终项目目标

最终项目应该能够做到：

> 用户不需要修改核心代码，仅通过配置，就可以创建不同类型的 Agent，并为 Agent 配置模型、Prompt、Tools、Knowledge、Memory 和 Workflow。

最终形成：

```text
                Agent Platform
                      │
       ┌──────────────┼──────────────┐
       ↓              ↓              ↓
     Agent           Tools        Knowledge
       │              │              │
       ↓              ↓              ↓
    Workflow       MCP/API         RAG
       │
       ↓
    Memory
       │
       ↓
  Evaluation
       │
       ↓
 Trace / Observability
```

项目完成后，应具备：

* 可运行
* 可配置
* 可扩展
* 可测试
* 可部署
* 有完整 README
* 有架构图
* 有 Demo
* 有 Evaluation Results

> **分阶段达成（下位文档 0.5.1/7.9 DoD）**：上面这份"最终目标"是**项目整体**的标准，不是第一阶段的标准。第一阶段（M1–M3，2–3 周）的验收 = 0.5.5 的 8 步演示脚本跑通（README 里如实标注哪些是 MVP、哪些是 Backlog）；"Evaluation Results"在 MVP 中由 `scripts/evaluate.py` 的报告体现。这样既能**随时展示**，也不会因为"还没做完"而无法交付。

并能够作为简历中的核心 Agent 项目。
